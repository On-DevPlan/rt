# app-animation-asset-formats 学习笔记（2026-08-31 v4）

> **Topic:** basic
> **类型:** 学习模式(基础知识概念)
> **版本:** v4（相对 v3：新增「像素画角色动画回收流水线」与「Web 上 GIF 的真实地位 + 自定义鼠标指针」两节；v1/v2/v3 内容全部保留）

## 1. 核心概念

App 动效资产的本质只有两大类：**位图动画/视频**（每一帧都是印死的像素）和**结构化描述**（一份「动画乐谱」，记录元素如何随时间变换，由端上播放器实时渲染）。GIF、APNG、WebP、MP4 属于前者；Lottie、PAG、SVGA、Rive 属于后者。行业里"红包开启""年度总结"这类动效，主流载体是后者，不是 GIF。按钮微交互靠代码与矢量描述，离视频最远。手里的视频素材按来源选路线；而**像素画视频是"视频回收"的唯一最佳特例**——信息被放大器盖住但没丢，可以近乎无损还原成 sprite sheet。

## 2. 解决什么问题

设计师在 AE（After Effects）里做出复杂动效后，工程师面临的问题：如何把这个动效还原到 iOS/Android/Web 三端？逐帧导出图片体积爆炸；手写代码还原成本高且失真；GIF 有 256 色 + 无半透明的硬伤。于是出现两条路线：

- **描述式**：导出 JSON/专用文件 + 各端装一个播放器 SDK，渲染结果接近 AE 原稿，文件只有几十~几百 KB；
- **视频式**：直接发视频文件，靠编码器把体积压到最小，代价是失去交互与动态数据能力、透明通道要 hack。

微交互场景（点击按钮出特效）在此基础上多一条硬约束：**延迟与状态**——反馈必须当帧出现，且要能被输入打断、暂停、反向，这直接排除了视频。

实战中还差两块：**成品视频素材**（无 AE 源）怎么进入体系；**像素画角色视频**（待机/跑动循环）怎么变成开发可用的资产。

## 3. 关键机制 / 组成

**位图动画三兄弟（序列帧思想）**

- **GIF** — 256 色调色板 + LZW 压缩 + 1-bit 透明（某一种颜色整体透明，无半透明 → 边缘毛边）— 上古格式，体积大、画质差，现代 UI 动效基本弃用，但在零 JS 环境与像素画场景仍有领地。
- **APNG** — PNG 格式扩展，多帧存放，8-bit alpha 全彩半透明；老播放器兼容降级显示第一帧 — 全彩透明小动效的稳妥选择。
- **Animated WebP** — WebP 容器装多帧，有损/无损均可带 alpha — 比 GIF 小 25~60%，现代浏览器/系统全支持。

**结构化描述阵营（乐谱 + 演奏者）**

- **Lottie**（Airbnb 开源）— AE 经 Bodymovin 插件导出 JSON，各端 lottie-android / lottie-ios / lottie-web 渲染 — JSON 是明文，**运行时可替换文本/颜色/图片**，这是"年度总结"类数据驱动动画的命脉；支持 marker/playSegments 分段播放；缺点：只支持 AE 特性子集，复杂粒子/模糊会丢失或失真，且本质是时间线、无真正状态机。
- **PAG**（腾讯开源）— AE 全特性导出为单一二进制 `.pag`，C++ 渲染引擎（libpag）尽量还原 AE 所有效果，另支持服务端批量渲染出视频 — 还原度最高、文件更小，QQ/微信红包封面等腾讯系场景的主力；生态开放度不如 Lottie。
- **SVGA**（YY 开源）— `.svga` 文件实为 zip：PNG 序列 + 描述变换的 JSON，本质是"打包好的序列帧 + 播放编排" — 直播礼物动效常用，实现简单但体积比真矢量方案大。
- **Rive** — 新一代设计工具 + 运行时，动画带**状态机**可响应交互输入（hover/press/release 切换状态、反向播放、输入驱动），运行时极小 — 交互式 UI 动效的新方向。

**Alpha 视频的三个 hack（MP4 标准流无透明通道）**

- **左右分屏 mask** — 视频左半放彩色画面、右半放灰度 alpha mask，播放时 shader 逐像素采样合成 — iOS/Android 直播全屏礼物最常见做法，对编码器零要求。
- **HEVC with Alpha** — 苹果私有扩展，HEVC 带辅助 alpha 层，AVPlayer 原生播放 — 仅 iOS 侧。
- **WebM (VP9) 原生 YUVA** — 容器/编码标准本身支持 alpha — Android（ExoPlayer）与 Chrome 可播，iOS Safari 不支持 WebM，跨端需备两份。

**视频素材接入开发：四条路线（按来源决策）**

- **有 AE 源工程 → 正道**：视频多半本来就是 AE 渲染导出的成品，乐谱原本就存在——向设计要源文件，Bodymovin 导出 Lottie 或 PAG 插件导出 `.pag`。Lottie/PAG 是 AE 的**导出格式**，不是视频的**转换目标**。
- **无源工程 + 短小（≤2~3s、小尺寸）→ 位图动画**：ffmpeg 抠底出 alpha 后转 APNG/WebP；体积随时长与分辨率平方级膨胀，只救得了短效果。
- **无源工程 + 较长/复杂、纯播放 → alpha 视频**：WebM VP9（Android/Web 原生带 alpha）、iOS HEVC-Alpha、或左右分屏 mask MP4（跨端通吃，直播礼物级方案）。
- **需要交互/运行时改内容 + 无源工程 → 只能重做**（AE 或 Rive）：视频与位图动画都是死像素，没有反推乐谱的捷径；实拍类视频天然只能走视频路线。

**"视频转 Lottie"为何不成立（与像素画例外的分界）**

- Lottie 描述的是形状与变换（矢量），视频是逐帧像素（位图）——从像素反推矢量描述即 rotoscoping/曲线拟合问题，没有可用的工程化工具。
- 社区存在把视频帧作为**图片层**塞进 Lottie 的脚本，产物 = 序列帧套壳：体积等于帧数之和、失去矢量与数据绑定意义，公认反模式；真要位图不如直接 APNG/WebP。
- **像素画是例外区**：它的"素材"本来就是离散像素网格，视频只是放大+封装的外壳——还原的目标是位图帧而非矢量乐谱，恰好落在工具可及范围内。

**像素画角色动画（待机/跑动）：从视频到 sprite sheet 的回收流水线**

- **原理**：像素画原生分辨率极低（角色常见 32×32 / 64×64 逻辑像素），视频里只是被整数倍（2×/3×/4×）放大——信息没丢，只是被放大器与压缩噪声盖住，可以"考古式复原"。
- **流水线**：抽帧 → 缩回原生分辨率 → 对齐网格 → 调色板归一 → 抠底 → sprite sheet + JSON。
- **抽帧去重** — `ffmpeg -i in.mp4 -vf mpdecimate frames/%03d.png` — 像素动画原生仅 8~12fps，视频里大量复制帧，mpdecimate 丢重帧直接砍半工作量。
- **缩回原生分辨率（关键步）** — 判定放大倍数后 `scale=iw/N:ih/N:flags=neighbor`（最近邻）— 把抗锯齿糊边与压缩噪点还原成锐利像素网格；直接拿原视频帧进开发是错的。
- **调色板归一** — 量化回原调色板、转索引色 PNG（P 模式）— 消除压缩漂移，顺带把体积压到最小。
- **抠底** — 纯色底用调色板映射（背景色索引 → 透明）比 colorkey 稳，不会吃掉深色描边 — 真像素画无抗锯齿半透明边，抠得干干净净。
- **产出 sprite sheet（精灵图/雪碧图）+ JSON 元数据** — 所有帧排进一张网格图 + 帧坐标/时长描述 — 游戏与 Web 角色动画的标准资产格式；**Aseprite**（像素画行业标准工具）负责修帧并导出 sheet+JSON，ffmpeg `tile` 滤镜亦可拼图。
- **分循环导出** — idle（待机，典型 2~8 帧）与 run（跑动，典型 6~12 帧）各自一份 sheet — 不同动作不同帧数，混在一张图里徒增元数据复杂度。
- **为什么角色用 sprite sheet 而非 GIF** — Web 上 GIF 播放控制几乎为零（不能暂停/变速/反向）；sprite sheet + CSS `steps(N)` 或 Canvas 逐帧渲染，播放/暂停/反向/换向（跑动左右翻面）全在自己手里，且只占一张纹理。

**GIF 在 Web 上的真实地位与自定义鼠标指针**

- **GIF 剩余的两块领地** — 零 JS 环境（GitHub README / markdown 文档 / 邮件 / 论坛，单文件 + 全端自动播放不可替代）与像素画舒适区（256 色对有限调色板无伤）— 观察"Web 上 GIF 仍常见"成立，但主要在这两块。
- **UI 动效里 GIF 已让位** — CSS 动画、Lottie-web、APNG/WebP 是一等公民。
- **自定义鼠标指针的真相** — 原生 `cursor: url()` 对静态图支持普遍，动画光标支持不可靠（.ani 为 IE/旧 Windows 时代产物，各浏览器对 GIF 光标表现不一）— 现代做法是 **JS 自定义光标**：隐藏系统光标 + `pointer-events:none` 的跟随元素，内部装 Lottie/精灵图/CSS 动画，完全可控；所以站上看到的"鼠标 GIF 动画"多半是零 JS 妥协或老方案，非现代主流。

**alpha 抽取与瘦身要点（假设素材为纯色/绿底 MP4 的常见情况）**

- **先确认是否带 alpha**：MP4(H.264) 一定没有；WebM 可能有——ffprobe 看 pix_fmt 是否带 `yuva`。
- **抠底**：chromakey/colorkey 滤镜（绿底抠色、白底 colorkey），alpha 输出走 `yuva420p`。
- **短小转动图**：抠底后 `-c:v libwebp -pix_fmt yuva420p -loop 0` 出 WebP（或 APNG）。
- **较长走分屏 mask**：split → 抠色成 alpha → alphextract 转灰度 mask → hstack 左右拼接；端上 shader 取左半 RGB + 右半 R 通道合成。
- **通用瘦身**：去音轨(-an)、裁时长、压 720p、30fps。

**按钮微交互动效（点击反馈）——载体阶梯**

- **原生平台动画** — UIKit/Core Animation、Jetpack Compose animation/MotionLayout、CSS transition — 几何反馈（位移/缩放/弹性/变色）首选：零依赖、零延迟、天然可交互；按压缩放、水波纹属于此类。
- **Lottie** — 一次性**爆发效果**的事实标准：点赞炸爱心、按钮礼花、图标碎裂重聚 — JSON 几 KB~几十 KB，预加载后首帧即出；交互仅限"跳段播放"。
- **Rive** — 需要**状态**的交互首选：hover/press/release 状态切换、取消点赞的反向变形 — 状态机让动画真正被输入驱动。
- **序列帧老派做法** — Android AnimationDrawable / iOS `animationImages` / 前端 Canvas 逐帧 — 简单直观，但内存 = 帧数 × 单帧尺寸，只适合帧少图小。
- **原生粒子系统 / Canvas/WebGL** — **大量重复实例**的特例：直播间点赞飘满屏的小心心 — 数百实例并发时 Lottie 每实例一层渲染会卡，粒子引擎（发射器+生命周期）才是正解。

**为什么按钮特效不用视频（视频的三个死穴）**

- **起播延迟**：解码器初始化约百 ms 级，点击反馈要求当帧响应；
- **不可交互**：按下停住、松手回弹、反向播放——视频是只进不回的时间线；
- **成本不摊销**：0.5~1 秒的效果承担解码器内存与起播开销不划算；视频的定位是「长且无交互」（全屏开屏、直播大礼物、过场片段）。

**数据驱动动画的特殊形态**

- **年度总结动画**（Spotify Wrapped / 网易云年度报告类）— 核心是千人千面：同一模板 + 每个用户的运行时数据。主流实现为 Lottie/PAG 运行时替换文本层，或 WebView 内 H5（CSS/Canvas）动画；服务端逐用户渲染视频的成本在实践中不可接受。

## 4. 类比与心智模型

- GIF/APNG/WebP = **翻页小人书**——每一页都印死，翻得快但改一个字要重印整本。
- Lottie/PAG = **动画乐谱**——只记录"哪个音符何时响起"，演奏时（运行时）可以随意换词改调。
- Alpha 视频分屏 = **带蒙版的电影胶片**——画面和剪影并排印在同一段胶片上，放映员（shader）现场对齐叠合。
- 视频转 Lottie = **从出版成书反推作曲家的手稿**——书能读，乐谱回不来；真需要乐谱就得找到作曲家（AE 源工程）重抄，或按书重新编曲（重做）。
- 像素画回收 = **考古复原**——模糊的壁画（视频）按网格残迹还原出原始砖块（逻辑帧）；信息没丢，只是被放大器盖住了。
- sprite sheet vs GIF = **乐谱分册 vs 整本胶装**——按动作分册（idle/run 各一）随取随翻任意重放；胶装 GIF 只能从头翻到尾。
- 按钮微交互选型 = **乐器分工**——节拍器（原生动画）打基础节奏，华彩（Lottie）负责炸场，即兴互动（Rive）看观众反应，交响乐（视频）只在正式大舞台上演奏。
- 记忆三问：**要不要透明？要不要运行时改内容？要不要还原多复杂的 AE 特效？** 微交互再加两问：**延迟敏不敏感？要不要状态？** 素材接入再加两问：**有没有源工程？是不是像素画？**——答完，路线自动浮现。

## 5. 常见误区

- "动效资产就是 GIF"——GIF 的 256 色与 1-bit 透明使其在现代 UI 动效中基本出局，只在零 JS 环境与像素画场景坐稳。
- "MP4 天然支持透明背景"——H.264/HEVC 标准流没有 alpha 通道，一切透明视频都是分屏 mask / 私有扩展 / VP9 这类手段的产物。
- "Lottie 能完美还原 AE 一切特效"——Lottie 只覆盖 AE 特性子集，粒子、复杂模糊、部分表达式会丢；需要高还原度时用的是 PAG 这类全特性方案。
- "年度总结动画是视频"——多数是数据驱动的结构化动画（Lottie/PAG/H5），逐用户渲染视频的成本结构不成立。
- "点击特效也可以用视频"——起播延迟、不可交互、成本不摊销三重不匹配；特效越小越靠代码/矢量，越大才越靠视频。
- "Lottie 就是交互动画"——它是时间线，交互只是"跳到某段播"；真正的状态机交互是 Rive 的主场。
- "找个工具把视频转成 Lottie 就能用"——转换工具至多把帧塞成图片层（序列帧套壳），体积与灵活度两头落空；正确动作是找 AE 源工程或按路线转 APNG/WebP/alpha 视频。
- "像素画视频直接拿去用就行"——不缩回原生分辨率就带着抗锯齿糊边与压缩噪点；必须最近邻缩回逻辑分辨率再做资产，否则网格是糊的。
- "Web 上的鼠标动画都是 GIF"——现代主流是 JS 自定义光标（跟随元素内装任意渲染物）；原生动画光标支持不可靠，GIF 光标多见于零 JS 妥协或老站。

## 6. 延伸主题

- 视频编码基础：H.264 / HEVC / VP9 / AV1 的差异与码率-体积权衡
- ffmpeg alpha 滤链：chromakey / colorkey / alphamerge / alphextract 的组合用法
- sprite sheet 深入：CSS steps() 逐格动画、JSON 元数据格式（Aseprite hash/数组导出）、纹理图集与打包器（TexturePacker）
- Lottie 与 PAG 的渲染架构对比（JSON 解释器 vs C++ 全特性渲染）
- Rive 状态机与交互式动效
- 原生动效系统：iOS Core Animation / Android Compose animation 的能力边界
- Canvas/WebGL 粒子系统：发射器、生命周期与批量渲染
- JS 自定义光标工程化：指针跟随插值、指针丢失处理（pointerlock/触屏降级）
- 游戏骨骼动画：Spine / DragonBones（与 UI 动效的分野）
- 服务端视频合成：FFmpeg 模板渲染、千人千面视频的工程化
